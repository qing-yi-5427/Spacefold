# 扫描性能实测

2026-10-12 在同一台 Windows 机器以普通权限测试三个官方 Windows x64 工具和 Spacefold release 核心。下表来自无并发编译负载的 `artifacts/benchmarks-release-final/results.json`，共 36 次执行，全部完成原始字节数与条目数核对。

环境：Windows 11 专业版 10.0.26300 x64，Ryzen 7 9800X3D（8 核 / 16 逻辑处理器），51,125,407,744 字节物理内存，C:/G: 均为 NTFS、本机 SSD。完整机器与卷元数据在同目录 `environment.json`；未把卷字母推断为某一个物理 SSD 型号。该轮 release probe SHA-256 为 `13f97aea615e7753bc4e955b5734754948d0d3e56e1c7b027c9b7c76fd86caab`。

## 数据与正确性

- 小文件夹具：100 个子目录，每个 1,000 个 128 字节普通文件，100,000 文件、100 目录；根外条目 100,100，总逻辑大小 **12,800,000 字节**。
- 实际目录：本机 MSVC `14.44.35207/include`，361 文件、14 目录；根外条目 375，总逻辑大小 **16,200,957 字节**。该目录在测试期间保持只读。
- 两组数据均已用独立枚举和各工具实际报告/合计核对。每一条有效结果含 `correctnessVerified:true`、实参、轮次、退出码与期望值；漂移或错误轮次不混入有效成绩。
- 初次使用 node_modules 发现 Vite 临时配置文件造成 512 字节漂移，因此最终实际目录改为稳定的 MSVC headers；旧漂移轮次不作为正式结果。

三轮顺序轮换，不清缓存、不提权、不调整系统安全设置。夹具生成和参考枚举已经预热缓存，准确标签是**自然暖缓存**。它不代表冷盘、网络盘、HDD 或整卷扫描。

## 各模式的工作量

| 模式 | 工作量 | 不能混淆的边界 |
|---|---|---|
| gdu summary | apparent 逻辑合计，不保完整浏览树 | 默认硬链接去重；本组普通文件没有该口径差异 |
| dua aggregate | apparent 逻辑合计，开启逐硬链接计数 | 没有 Spacefold 的完整 SQLite 浏览索引 |
| Spacefold kernel | 同一 Windows 元数据枚举与逻辑合计 | 这是剖析模式，不是完整应用扫描成绩 |
| gdu full tree | 完整树与 JSON 写出 | 其输出字段、格式与 SQLite 查询索引不同 |
| WinDirStat full tree | 普通权限 `/SaveTo` 完整树报告 | 不启用提权 MFT 加速；保存过滤设置必须固定 |
| Spacefold sqlite | 元数据、完整节点与索引持久化、目录合计、首批可浏览结果 | 默认延后单文件分配/身份细查，选中时测量；逻辑口径一致 |

参数、口径与官方依据见 [performance-method.md](performance-method.md)。本机 gdu 的默认 `max-cores` 为 16；dua 使用 `--threads 0`。保留各工具默认并发，不把另行固定并发的结果混入本表。

## 实际目录：MSVC headers

外部墙钟包含进程启动至退出，单位为秒。三轮按原始轮次顺序列出；峰值为 Windows 记录的该工具父进程峰值工作集，取三轮最大，单位 MiB。

| 模式 | 第 1 / 2 / 3 轮（秒） | 中位数（秒） | 最大峰值工作集（MiB） |
|---|---|---:|---:|
| dua aggregate | 0.0339 / 0.0358 / 0.0378 | 0.0358 | 12.04 |
| gdu summary | 0.0638 / 0.0619 / 0.0629 | 0.0629 | 15.06 |
| Spacefold kernel | 0.0333 / 0.0345 / 0.0343 | 0.0343 | 6.18 |
| gdu full tree | 0.0627 / 0.0674 / 0.0670 | 0.0670 | 17.24 |
| WinDirStat full tree | 0.3225 / 0.3094 / 0.3133 | 0.3133 | 53.16 |
| Spacefold sqlite | 0.1072 / 0.1216 / 0.1082 | 0.1082 | 8.84 |

Spacefold 完整 SQLite 流程中位数 0.1082 秒，低于本组 WinDirStat 的 0.3133 秒，但高于 gdu 完整树的 0.0670 秒。内部扫描耗时 72 / 73 / 73 ms；首批已提交可查询节点时间 41 / 41 / 43 ms。kernel 内部 1 / 2 / 1 ms 是枚举剖析指标，不能替代完整流程。

| dua aggregate | 0.0681 / 0.0503 / 0.0589 | 0.0589 | 12.23 |
| gdu summary | 0.0689 / 0.0865 / 0.0680 | 0.0689 | 41.24 |
| Spacefold kernel | 0.1178 / 0.1192 / 0.1186 | 0.1186 | 6.17 |
| gdu full tree | 0.1000 / 0.1019 / 0.1082 | 0.1019 | 67.95 |
| WinDirStat full tree | 0.6449 / 0.6391 / 0.6323 | 0.6391 | 65.15 |
| Spacefold sqlite | 1.1317 / 1.2058 / 1.0580 | 1.1317 | 43.46 |

本组 Spacefold 完整扫描仍慢于三款竞品：中位数约为 WinDirStat 的 1.77 倍、gdu 完整树的 11.11 倍。kernel 中位数 0.1186 秒，也高于 dua/gdu 的单纯合计模式。因此**尚未达到所有开源工具的小文件扫描速度**，不能因枚举内核较快而宣称完成流程性能相当。

完整 SQLite 内部耗时 1085 / 1162 / 1008 ms，首批已提交可查询节点为 127 / 122 / 120 ms。这里保留了完整节点、目录聚合与查询索引的持久化成本；任务运行期间即可分页浏览。终端 `firstOutputSeconds` 是 probe 最终摘要第一次写 stdout 的时间，不是 UI 首批结果时间；WinDirStat 的非空报告文件也不等同于完整报告写完。

## 测量边界与应用体验

工作集采样周期为 10 ms；原始日志同时保留父进程峰值和采样进程树峰值，后者是采样下界。短进程可能来不及取得进程树样本，采样值 0 表示**未捕获**，不能解释为零内存。上表使用系统记录的父进程峰值，避免把漏采解释为内存优势。

Rust probe 的内存不含 Tauri/WebView2。完整桌面应用另测 exe 与 WebView2 进程树的峰值和交互反馈；不能把核心内存列为整个 GUI 的占用。空间图、透镜和虚拟树的查询/渲染数据也单独记录，不用百万条合成数据库速度替代真实磁盘扫描速度。

实际 Tauri/WebView2 窗口对 500 文件扫描进行了 600 / 800 / 1000 CSS px 高度测试，树表完整可见行 11 / 16 / 22，实际挂载 21 / 26 / 32 行，状态栏贴底、详情独立滚动；搜索可直接定位第 420 个文件。证据为 `artifacts/native-height/metrics.json`、`artifacts/native-real-ui/results.json` 和对应原生截图。这证明已接通窗口自适应与按页查询，并不是百万文件真实磁盘扫描性能证明。

百万条合成数据库的分页与 CSV/JSON/XLSX 导出重读验收由独立规模测试记录，必须与本页真实目录扫描分开阅读。CPU/I/O 等未在这份外部结果结构记录的指标不作数值结论。此轮后续修复若改变枚举/落库路径，应按同一脚本复测，并保留这一轮日志作历史记录。
